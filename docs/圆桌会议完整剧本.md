# AI 商品委员会 · 圆桌会议完整剧本

> 本文档是 SKU Hunters 系统的心脏：定义五幕会议中每位 Agent 的输入输出契约、发言模板与冲突处理规则。
> 可直接作为工程实现依据——每个契约对应一个 Pydantic Schema，每个发言模板对应一组 Prompt。

---

## 〇、总则

### 0.1 三条铁律

| 铁律 | 内容 | 违反后果 |
|:---|:---|:---|
| **信息隔离** | 每位 Agent 只看得见自己职责内的数据源，看不见其他 Agent 的原始数据 | 圆桌退化为剧本表演，本次评审作废 |
| **证据强制** | 任何结论必须挂 EvidenceRef（url + title + snippet），无证据不得发言 | ReviewAgent 直接打回，标记 target_node 重跑 |
| **"无法判断"合法** | 数据不足时允许且必须输出"无法判断"，禁止编造 | 编造证据视为系统级 bug，进入对抗测试集 |

### 0.2 会议状态机

```
CREATED
  → BRIEF_LOCKED        （输入确认：品类+市场+预算+权重模板）
  → ACT1_INSIGHTS       （第一幕：三官并行陈述，互不可见）
  → ACT1_GATE           （ReviewAgent 质检：证据完整性检查）
  → ACT2_IDEATION       （第二幕：创意官生成方案）
  → ACT2_CHALLENGE      （质询环节：洞察三官行使异议权）
  → ACT3_DUAL_REVIEW    （第三幕：商业官/全球化官双轨并行）
  → ACT4_DECISION       （第四幕：Decision Engine 合成建议书）
  → HUMAN_GATE          （挂起：等商品经理确认，唯一的人工决策点）
  → APPROVED / REVISED / REJECTED
  → （上市后）ACT5_RETRO （第五幕：学习官复盘）
  → LEARNED             （校准建议入库，等待人类批准后生效）
```

任一节点可被打断挂起（详见 5.5 打断机制），checkpoint 落盘，恢复后续跑。

### 0.3 通用发言卡结构

每位 Agent 的每次发言必须填充以下结构（口语化表达由模板生成，结构化数据进 Schema）：

```
【结论】一句话判断
【依据】分项论据，每条挂 EvidenceRef
【置信度】高（多源交叉验证）/ 中（单源可信）/ 低（推断）/ 无法判断（数据不足）
【保留意见】我主动声明的不确定性或反向信号
【对前置发言的回应】（仅第二幕以后）我同意/反对谁的什么观点，为什么
```

置信度不是装饰——Decision Engine 合成时，低置信度结论的权重自动降半。

## 一、第一幕：洞察陈述

**参与**：趋势官、用户官、IP官（三方并行）
**核心纪律**：三方互不可见对方产出——平行陈述，防止相互锚定。先看见别人的结论再组织自己的证据，是假圆桌最常见的作弊方式。
**本幕结束条件**：ReviewAgent 质检通过（证据完整性 + 无跨权限引用）。

---

### 1.1 趋势官 · 契约

**输入契约**

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| `brief.category` | string | 品类，如"潮玩" |
| `brief.market` | string | 目标市场地区码，如"TH" |
| `brief.time_window` | string | 可选，上市时间窗口 |
| `data_access` | 白名单 | **仅**：Google Trends、B站分区排行、社媒热搜快照 |

**禁止访问**：电商需求数据（用户官的）、IP 授权库（IP官的）、成本数据（商业官的）。

**输出契约**（对应 Schema：`FeatureMatrix`）

| 字段 | 类型 | 约束 |
|:---|:---|:---|
| `trends[]` | TrendItem 列表 | 每个关键词一条 |
| `trends[].heat_index` | float 0-100 | 三维度合成：水平 40% + 增速 40% + 广度 20% |
| `trends[].lifecycle` | enum | rising / peak / declining / unknown |
| `trends[].evidence_refs` | EvidenceRef[] | **每条趋势至少 1 条证据** |
| `summary` | string | ≤150 字 |
| `confidence` | enum | 高/中/低/无法判断 |

**发言模板**

> 【趋势陈述】
> 我监测到「{关键词}」当前热度指数 {heat_index}，处于{生命周期}阶段。
> 依据有三：① 搜索热度近 7 天均值 {level}，环比 {growth}%；② 关联上升查询 {breadth} 个；③ 跨平台信号：{平台对比描述}。
> 区域特征：{目标市场的具体表现}。
> 证据：{EvidenceRef 列表}
> 置信度：{高/中/低}
> 保留意见：{例如"该信号仅来自搜索数据，未经验证购买转化"}

---

### 1.2 用户官 · 契约

**输入契约**

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| `brief` | 同上 | 品类 + 市场 + 预算 |
| `data_access` | 白名单 | **仅**：电商评论、淘宝联想词（需求侧）、UGC 评论情绪 |

**输出契约**（对应 Schema：`UserSentiment`）

| 字段 | 类型 | 约束 |
|:---|:---|:---|
| `pain_points[]` | PainPoint 列表 | 每条含 description / frequency / severity |
| `motivation_tags[]` | string[] | 购买动机标签，如"收藏""社交分享""送礼" |
| `price_sensitivity` | object | 价格敏感区间，如 "¥39-79 敏感度最低" |
| `demand_signals[]` | 需求词列表 | 来自联想词的真实需求表达 |
| `product_form_signals[]` | string[] | 商品形态信号，如"娃衣/挂件/盲盒" |
| `evidence_refs` | EvidenceRef[] | 强制 |

**发言模板**

> 【用户洞察】
> 在{品类}/{市场}，我识别出的核心人群是 {人群画像}。
> 他们的前三大购买动机依次是 {动机1}（{占比}）、{动机2}、{动机3}。
> 未被满足的需求：{痛点清单，按频率排序}。
> 价格敏感区间：{区间及依据}。
> 从真实搜索行为看，消费者在主动找这些商品形态：{形态信号列表}。
> 证据：{EvidenceRef 列表}
> 置信度：{高/中/低}
> 保留意见：{例如"评论样本集中在已有购买者，潜在人群需求可能不同"}

---

### 1.3 IP官 · 契约

**输入契约**

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| `brief` | 同上 | |
| `data_access` | 白名单 | **仅**：IP 热度数据、授权信息库、历史联名案例库 |

**输出契约**（对应 Schema：`IPAssessment`）

| 字段 | 类型 | 约束 |
|:---|:---|:---|
| `ip_ranking[]` | IP 候选列表 | 每个含名称/热度/区域适配分 |
| `lifecycle_prediction[]` | 预测 | 每个 IP 的窗口期估计（如"6-9 个月"） |
| `regional_fit` | object | 目标市场匹配度 |
| `licensing_risk` | string | 授权风险提示（如"已被竞对接触"） |
| `evidence_refs` | EvidenceRef[] | 强制 |

**发言模板**

> 【IP 研判】
> 针对{品类}/{市场}，我推荐的 IP 优先级为：{排序列表}。
> 首选「{IP名}」的理由：当前处于{生命周期阶段}，预计窗口期 {时长}；{市场}区域适配度 {分}，依据：{区域偏好证据}。
> 授权风险：{风险声明，无则声明"无已知风险"}。
> 我不推荐的：{IP名}，原因：{过热衰退/授权成本超预算区间/区域错配}。
> 证据：{EvidenceRef 列表}
> 置信度：{高/中/低}
> 保留意见：{例如"生命周期预测基于历史同构曲线，黑天鹅事件不可排除"}

---

### 1.4 第一幕质检（ACT1_GATE）

ReviewAgent 在本幕结束时执行三项检查：

| 检查项 | 不通过的处理 |
|:---|:---|
| 每条结论是否挂 EvidenceRef | 打回对应 Agent，标注缺失项 |
| 是否存在跨权限数据引用（如趋势官引用成本数据） | 打回 + 系统日志记录（疑似权限泄漏） |
| 数据信号冲突是否已显式标注（如淘宝热但 B站冷） | **未标注即打回**——冲突不许藏着（详见第六章） |

## 二、第二幕：方案提出

**参与**：创意官（主角）+ 洞察三官（质询环节回归）
**核心纪律**：创意官**只看得见三份 Artifact，看不见原始数据**——它必须信任并引用上游结论，这正是"汇聚产生增量"的结构性保证。

### 2.1 创意官 · 输入契约

| 字段 | 来源 | 说明 |
|:---|:---|:---|
| `feature_matrix` | 趋势官 | 趋势结论（非原始数据） |
| `user_sentiment` | 用户官 | 需求结论（非原始数据） |
| `ip_assessment` | IP官 | IP 结论（非原始数据） |
| `brief.budget_range` | 用户输入 | 预算区间，硬约束 |
| `hit_case_library` | 飞书知识库 RAG | 历史爆品特征库 |

### 2.2 创意官 · 输出契约（Schema：`ProductProposal[]`，3-5 个）

| 字段 | 类型 | 约束 |
|:---|:---|:---|
| `name` | string | 方案名，如"桌面摆件系列" |
| `concept` | string | 一句话概念 |
| `product_form` | string | 商品形态，**必须来自用户官的形态信号或知识库** |
| `target_segment` | string | 目标人群 |
| `price_band` | string | 价格带，**必须落在预算区间内** |
| `source_map` | 溯源映射 | **每个方案要素标注依据了哪份 Artifact 的哪条结论** |
| `differentiation` | string | 与其他候选方案的差异点 |

**硬校验规则**（不通过则打回重生成）：
1. 方案间必须互异——形态/场景/价位至少两维不同，微调变体不算独立方案
2. `source_map` 必须覆盖三方 Artifact 各至少一条——只用趋势不用需求的方案是残次品
3. `price_band` 超预算区间直接拒绝

### 2.3 创意官 · 发言模板

> 【方案陈述】
> 综合三方洞察，我提出 {N} 个方向，它们互相差异，覆盖不同形态与场景：
>
> **方向{i}：{方案名}**
> 概念：{一句话}
> 形态：{商品形态}——依据用户官发现的"{形态信号}"
> 目标人群：{人群}——依据用户官画像
> 价格带：{价格带}——依据用户官价格敏感区间
> 搭乘趋势：{趋势}——依据趋势官"{结论}"
> 关联 IP：{IP}——依据 IP官"{结论}"
> 与其他方向的差异：{差异化说明}
>
> 保留意见：{例如"方向三的市场规模依据较弱，建议评审时重点关注"}

### 2.4 质询环节（ACT2_CHALLENGE）：洞察三官的异议权

创意官陈述后，趋势官/用户官/IP官**必须逐一回应**——这是防止"创意官曲解上游结论"的制度设计：

| 质询选项 | 含义 | 后续动作 |
|:---|:---|:---|
| **背书** | "该方案正确引用了我的结论" | 无 |
| **修正** | "方案引用我的结论但有偏差"（如夸大热度） | 创意官修订方案，无需重跑 |
| **反对** | "方案与我的结论冲突"（如用了我已声明衰退的 IP） | 触发冲突处理规则 6.4 |

**质询模板**（以 IP官为例）：

> 【质询回应】对方向{i}：{背书/修正/反对}
> 理由：{方案引用我的结论"{原结论}"，我的意见是……}
> {若反对}我建议的替代：{替代方案要素}

## 三、第三幕：双轨评审

**参与**：商业官、全球化官（**严格并行，互不可见对方产出**）
**核心纪律**：商业价值和市场策略是两个独立维度，任何一方先看到对方的分数都会产生锚定。两官同时对同一批 `ProductProposal[]` 独立评审。

### 3.1 商业官 · 契约

**输入**：`ProductProposal[]` + 成本数据 + 竞品数据 + 历史销售参照 + **权重配置**（来自 BRIEF_LOCKED）

**输出契约**（Schema：`OpportunityScore[]`，每方案一份）

| 字段 | 类型 | 约束 |
|:---|:---|:---|
| `dimension_scores` | 五维分项 | 趋势热度/用户需求/IP适配/竞争程度/历史相似，各 0-100 |
| `dimension_evidence` | 映射 | **每个分项挂对应 Agent 的证据** |
| `total_score` | float | 加权合成，权重取自配置 |
| `star_rating` | ★1-5 | 总评映射 |
| `risk_warnings[]` | string[] | 每条风险标注来源维度 |
| `confidence` | enum | 沿用上游最低置信度（置信度会沿链路衰减，不放大） |

**发言模板**

> 【商业评审】
> 三个方案的机会值评估完毕：
> 方案A {分} 分 {星级}——最强分项是{维度}（{分}），依据{来源Agent}的证据；主要风险：{风险}。
> 方案B ……
> 方案C ……
> 我的排序建议：{排序及一句话理由}。
> 保留意见：{例如"竞争程度维度数据较旧，实际竞争可能更激烈"}

### 3.2 全球化官 · 契约

**输入**：`ProductProposal[]` + 区域市场数据 + 节假日日历 + 本地化要求

**输出契约**（Schema：`GTMPlan[]`，每方案一份）

| 字段 | 类型 | 约束 |
|:---|:---|:---|
| `country_ranking[]` | 国家排序 | 含分批计划与依据 |
| `pricing[]` | 定价建议 | 每国货币+价格带 |
| `localization_notes[]` | 本地化要点 | 如"日本需礼盒装" |
| `launch_timeline` | 时间表 | 批次与间隔 |
| `evidence_refs` | EvidenceRef[] | 强制 |

**发言模板**

> 【上市策略】
> 建议分 {N} 批上市：首批 {国家}（{时间}，定价 {价格}），依据：{区域适配证据}；
> 第二批 {国家}（{时间}），观察首批 {指标} 后调整；
> {国家} 建议暂缓，原因：{依据}。
> 本地化要点：{逐条列出}。
> 保留意见：{例如"第二批计划依赖首批数据，存在不确定性"}

### 3.3 并行纪律

- 两官**同时启动**，各自 checkpoint，互不等待
- 任一方失败不阻塞另一方；单边产出也可进入第四幕（在建议书中标注"缺失维度"）
- 两官产出完成后才允许互相可见——锚定防护到此解除

## 四、第四幕：决策输出

**参与**：Decision Engine（非 Agent，是规则引擎）→ HUMAN_GATE（商品经理）
**核心纪律**：Decision Engine 只做合成与呈现，**不做任何未被授权的推理**——它不产生新事实。

### 4.1 Decision Engine · 契约

**输入**：`OpportunityScore[]`（商业官）+ `GTMPlan[]`（全球化官）+ 全程质询记录

**输出契约**（Schema：`立项建议书`）

| 区块 | 内容 | 数据来源 |
|:---|:---|:---|
| 候选方案排序 | 按机会值降序 | 商业官 |
| 每方案决策建议 | approve / hold / reject（≥80 / 60-79 / <60） | 规则映射，非模型判断 |
| 五维分解剖 | 每方案的分项得分与证据 | 商业官 |
| 上市建议 | 国家批次、定价、本地化要点 | 全球化官 |
| **分歧记录** | 评审过程中的所有冲突与质询 | 全程记录（见第六章） |
| 待定事项 | 需要人类补充决策的开放问题 | 各 Agent 保留意见汇总 |
| 风险提示 | 按严重度排序 | 商业官 + 各 Agent 保留意见 |

**决策建议的映射规则是写死的**，不允许 LLM 自由发挥：

```
total_score ≥ 80 且无双官重大保留意见 → approve
total_score 60-79 或存在保留意见      → hold（标注待补数据）
total_score < 60                       → reject（标注主因维度）
```

### 4.2 HUMAN_GATE：唯一人工决策点

系统 interrupt 挂起，向商品经理呈现建议书。经理可选动作：

| 动作 | 系统行为 |
|:---|:---|
| **批准** | 状态 → APPROVED，写入多维表格台账，进入上市流程 |
| **调整权重重跑** | 回到评分合成节点（秒级，洞察层不动），重新呈现 |
| **打断质疑** | 按 5.5 三类打断路径处理 |
| **否决** | 状态 → REJECTED，**必须填否决理由**——这是学习官最宝贵的负样本 |

**否决必须留理由**是制度设计：人否决 AI 的高分方案，恰恰是人机认知差的最大信号源。

## 五、第五幕：复盘（上市后触发）

**参与**：学习官
**触发条件**：方案上市 + 结果数据回流（生产环境：POS/ERP；比赛环境：电商公开代理数据 / 时光机回测）

### 5.1 学习官 · 契约

**输入**：立项记录（当初的五维评分+证据+人工决定）+ 上市后实际结果（销量达成率、动销率、售罄率、社媒声量延续性）

**输出契约**（Schema：`RetroReport`）

| 字段 | 内容 |
|:---|:---|
| `prediction_gap` | 预测 vs 实际，逐维度偏差 |
| `attribution` | 归因：爆/哑分别由哪个信号驱动 |
| `new_dimension_candidates[]` | 新发现的评估维度（如"包装礼品化程度"） |
| `weight_calibration_advice` | 权重校准**建议**（仅建议，人类批准后生效） |
| `agent_performance` | 各 Agent 本期预测准确度排名 |

### 5.2 学习官 · 发言模板

> 【复盘报告】
> 本期对照：{方案}预测 {分} 分，实际表现 {结果}。
> 逐维度偏差：趋势维度 {准/偏}（{说明}）；需求维度……
> 归因结论：{哪个信号是真的，哪个信号误导了}。
> 新发现：{新维度}，建议纳入评估清单。
> 校准建议：{权重调整建议}，依据最近 {N} 期数据——**提请商品委员会批准，批准后影子运行 {N} 期再切换**。
> 飞轮状态：预测偏差率环比 {收窄/扩大} {X}%。

### 5.3 复盘纪律（迭代四纪律的重申）

1. **样本量纪律**：单次结果不调权重，N 期积累才提建议
2. **版本控制**：每次变更存版本、可回滚
3. **影子模式**：新权重并行评分验证后才切换
4. **人类批准制**：学习官无自动改参权

## 六、冲突处理规则

> 圆桌会议的价值不在"达成一致"，在**把分歧结构化地暴露出来**。本章是本剧本的灵魂。

### 6.1 冲突分类总表

| 编号 | 冲突类型 | 发生在 | 处理原则 |
|:---:|:---|:---|:---|
| C1 | 数据信号冲突 | 第一幕（各官内部） | 如实并陈，禁止调和平均 |
| C2 | 结论引用偏差 | 第二幕质询环节 | 修正或反对，创意官修订 |
| C3 | 评分分歧 | 第三幕（双官之间） | 不强制一致，分歧写入建议书 |
| C4 | 人机冲突 | HUMAN_GATE | 人赢，但必须留理由 |
| C5 | 证据不足 | 任意环节 | 降级声明"无法判断" |
| C6 | 打断冲突 | 任意环节 | 按最小失效重跑路径 |

---

### 6.2 C1 · 数据信号冲突

**规则：不调和、不平均、不隐瞒。先发现的一方必须显式标注，ReviewAgent 强制检查。**

**真实实例**（来自本系统实测数据）：

> 趋势官监测 Labubu：淘宝联想词返回 10 条真实需求词（"拉布布娃衣""拉布布盲盒"，消费需求信号强），但 B站 5 分区 474 个排行视频中命中 0 个（UGC 创作信号为 0）。

**处理流程**：

```
1. 趋势官在发言卡的【保留意见】中强制声明：
   "消费需求信号（淘宝）与内容创作信号（B站）背离"
2. 不做简单平均，而是做生命周期推断：
   B站冷 + 淘宝热 = 该 IP 大概率处于「扩散后期」——
   核心圈层创作已退烧，大众消费需求仍在
3. 该推断本身标注置信度「中」，挂两类证据
4. 此冲突记录直达建议书「分歧记录」区块，
   商品经理看到的是完整的矛盾，不是被抹平的结论
```

**为什么不平**均：信号冲突本身是最有信息量的发现——它揭示趋势所处阶段。平均掉等于把最重要的发现销毁。

### 6.3 C2 · 结论引用偏差（质询环节）

**场景**：创意官方案写"搭乘趋势：Labubu 上升期"，但趋势官原话是"上升期末段，预计 2 个月内见顶"。

**处理**：

| 偏差程度 | 质询动作 | 后续 |
|:---|:---|:---|
| 轻微（措辞偏差） | 修正 | 创意官修订表述，不重跑 |
| 中等（程度夸大） | 修正 | 创意官修订 + 该方案 source_map 重新标注 |
| 严重（结论反转，如把"衰退"引用为"上升"） | 反对 | 方案打回创意官重生成，**该次引用错误记入创意官性能档案**，供学习官评估 |

### 6.4 C3 · 评分分歧（双官之间）

**场景**：商业官给方案 A 打 83 分（商业上成立），全球化官给出"首批国家仅 2 个、市场规模有限"的策略结论（策略上偏保守）。

**规则：双轨不强制一致。** 分歧不是系统故障，是决策信息：

1. 两份产出**原样并列**进入建议书，Decision Engine 不做"和事佬"
2. 建议书中生成"分歧提示"：`该方案商业评分高但目标市场容量有限，请委员会权衡「高毛利小市场」vs「走量大众市场」的战略取向`
3. 此类分歧通常映射到**战略意图**（走量款 vs 利润款）——恰好在 BRIEF_LOCKED 阶段可由经理通过权重模板预先表达

**禁止行为**：Decision Engine 不得自行发明"调和分"，不得用 LLM 生成一段看似圆融的和稀泥文字。

### 6.5 C4 · 人机冲突

**规则：人赢。无条件。但必须留痕。**

| 人的动作 | 系统处理 |
|:---|:---|
| 批准低分方案 | 允许，强制填写理由（如"该 IP 创始人即将来访，有战略意义"） |
| 否决高分方案 | 允许，强制填写理由 |
| 修改方案要素 | 允许，修改内容挂到 source_map 上，标注"人工修订" |

**留痕的价值**：人机冲突记录是学习官的第一优先级学习素材——
- 若人频繁否决高分方案且事后证明人对 → 说明评分模型漏了人能感知到的维度（学习官应提出新维度候选）
- 若人否决高分方案但事后证明 AI 对 → 复盘会上呈现给委员会，逐步建立人对系统的校准信任

**AI 没有"说服权"**：系统不得生成"您确定要否决吗？该方案其实……"这类劝阻话术。呈现证据是职责，影响决策是越界。

### 6.6 C5 · 证据不足

**规则：降级声明是荣誉，编造证据是事故。**

分级处理：

| 情形 | 系统行为 |
|:---|:---|
| 单源证据不足 | 置信度标「低」，建议书自动降权 |
| 关键维度无数据 | 输出"无法判断" + 列出**补数建议**（如"建议采购 XX 数据/发起 XX 调研"） |
| 全案数据不足 | 整体输出 hold，而非硬凑一个分数 |

"无法判断 + 补数建议"本身是有价值的产出——它告诉企业**该买什么样的数据**，这是决策支持系统的正当职责。

### 6.7 C6 · 打断冲突（衔接 5.5 三类打断路径）

打断注入的新信息若与已有 Artifact 冲突（如经理说"该 IP 已被竞对签走"，而 IP 官刚推荐它）：

1. 人工注入信息优先级最高，直接覆盖
2. 沿依赖图向下游标脏：IP官结论失效 → 创意官方案失效 → 双官评审失效
3. 从最早失效节点（IP官）起重跑，上游不受影响的部分复用 checkpoint
4. 全程保留两版记录（打断前/后），供学习官分析"什么信息是系统没抓到的"

## 七、完整示例：一次基于真实数据的会议实录

> 以下实录基于 2026-08-07 本系统实测抓取的真实数据（淘宝联想词 API + B站分区排行 API），展示五幕流程的完整形态。输入：`品类=潮玩，市场=中国（演示环境），预算=中档`，权重模板=默认。

### BRIEF_LOCKED

- 品类：潮玩 | 市场：CN | 预算区间：中档（排除头部天价 IP）
- 权重：趋势 35% / 需求 25% / IP 20% / 竞争 10% / 历史 10%（默认模板）
- 候选 IP 池：Labubu、Chiikawa、线条小狗

---

### 第一幕 · 洞察陈述（三官并行，互不可见）

**🔍 趋势官**：

> 【趋势陈述】我监测到三个候选 IP 的内容创作信号：扫描 B站生活/时尚/动画/游戏/鬼畜 5 个分区共 474 个排行视频，Labubu 命中 0、Chiikawa 命中 0、线条小狗命中 0；阳性对照「原神」命中 4 个、总播放 227 万，证明监测链路有效。
> 生命周期判断：三个 IP 在 UGC 创作侧均无当前曝光信号，**倾向判断为扩散后期或平台迁移期**。
> 证据：B站分区排行 API 快照（2026-08-07）
> 置信度：中（单平台信号，未交叉验证其他内容平台）
> 保留意见：B站排行 ≠ 全网创作热度，抖音/小红书数据为快照待补。

**👥 用户官**：

> 【用户洞察】真实搜索行为显示三个 IP 的消费需求均活跃：Labubu 关联需求词 10 条（拉布布娃衣、拉布布挂件、拉布布盲盒等），Chiikawa 10 条（玩偶/挂件/公仔/周边），线条小狗 10 条（盲盒/挂件/玩偶/手机壳）。
> 商品形态信号高度集中：**娃衣、挂件、盲盒、公仔**四个形态在三个 IP 上重复出现——消费者需求表达清晰。
> 证据：淘宝搜索联想 API（2026-08-07）
> 置信度：中（联想词热度权重为相对值，无绝对量级）
> 保留意见：搜索联想 ≠ 成交，转化率未知。

**⚠️ ReviewAgent 在 ACT1_GATE 触发 C1 规则**：

> 检测到信号冲突：用户官的需求信号（活跃）与趋势官的创作信号（0 曝光）背离。已强制两位 Agent 在保留意见中显式声明，冲突记录已写入会议档案，直达建议书分歧区块。**禁止任何一方修改结论去"配合"另一方。**

**🧸 IP官**：

> 【IP 研判】综合生命周期与授权可得性：三个 IP 均为治愈系，同构生命周期曲线显示该类 IP 窗口期约 6-9 个月。结合趋势官的创作信号冷却 + 用户官的需求信号仍热，判断三 IP 处于**「创作退烧、消费延续」阶段**——联名策略应走「成熟形态快反」而非「话题引爆」路线。
> 授权风险：无已知风险（演示环境，授权库为样例数据）。
> 置信度：中。

---

### 第二幕 · 方案提出

**🎨 创意官**（输入：三份 Artifact + 知识库 + 预算约束）：

> 【方案陈述】综合三方洞察，提出 3 个互异方向：
>
> **方向一：IP 娃衣系列**——形态依据用户官"娃衣"信号（三 IP 共同高频词）；差异点：悦己+社交晒图场景；价格带 ¥39-59。
> **方向二：盲盒挂件系列**——形态依据"挂件+盲盒"双信号；差异点：随身佩戴场景，入门价位引流款；价格带 ¥29-39。
> **方向三：联名收纳摆件**——针对用户官识别的"收藏后收纳"衍生痛点；差异点：功能型差异竞争，避开纯摆件红海；价格带 ¥59-79。
>
> 三个方向均落在中档预算内，均未采用头部天价 IP。
> 保留意见：由于趋势信号显示创作侧冷却，三个方向都不应以"话题营销"为上市主策略，建议评审关注。

**质询环节**：
- 趋势官：**背书**（附加强调：勿用话题引爆策略）
- 用户官：**背书**
- IP官：**修正**——"方向三'收纳摆件'超出了我给出的 IP 适配范围，收纳品类与治愈系 IP 的情感联结弱，建议标注该方向 IP 适配分下调"→ 创意官修订 source_map

---

### 第三幕 · 双轨评审（并行，互不可见）

**💰 商业官**：

> 【商业评审】机会值评估：
> 方向一（娃衣）76 分 ★★★★——用户需求分项最高（真实搜索词密集），趋势分项被创作冷却信号拉低；风险：娃衣复购依赖 IP 持续热度。

> 方向三（收纳摆件）64 分 ★★★——差异化好但 IP 适配分经质询下调，市场规模证据最弱。
> 排序建议：一 > 二 > 三。

**🌍 全球化官**（演示环境仅评国内，略）——并行纪律示例：若其在真实环境运行，将与商业官同时产出。
