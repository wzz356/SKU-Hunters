# SKU Hunters · AI Product Committee —— 项目全景设计文档

> 名创优品 × AI 先锋未来人才大赛 · 参赛方案完整思考
> 一句话定位：不是让 AI"帮你干活"，而是让 AI"替委员会先开一次会"——把爆款从"灵光一现"变成"数据可推演的确定选择"。

---

## 一、项目缘起：场景、流程与痛点

### 1.1 源自什么场景

源自名创优品商品开发部门每个季度都在重复的真实场景：**"711 战略"下的选题会**。每 7 天上 100 款新品，这 100 款从约 1 万个设计方案里选出来——商品委员会每周的核心动作是：**用 1% 的通过率，从上万个候选里押注下一批可能爆的款**。

这个场景有一个扎心的数据背景：名创 2025 上半年收入同比 +21%，但净利润同比 -22.6%，内地同店 GMV 下滑。**"推得多"没有转化成"卖得好"**——上新机器转得飞快，但命中率瓶颈卡住了整个商业模型。这就是命题的真实压力来源。

### 1.2 原本的流程

```
市场研究部手动搜集趋势（3-5天）
    → 输出趋势PPT
        → 商品企划凭经验+趋势报告写方案
            → 商品委员会周会评审（2小时，十几个方案过一遍）
                → 通过的打样、订货、上市
                    → 上市后2-4周数据回来，人工复盘
```

### 1.3 最难把控的环节（按痛苦程度排序）

| 排序 | 环节 | 为什么最烦 |
|:---:|:---|:---|
| **1** | **评审会本身** | 信息割裂的总爆发点。市场的人懂趋势但不懂毛利，财务懂毛利但不懂 Z 世代，海外运营懂本地市场但不在会上。**两小时会议里没有任何一个人掌握完整信息**，决策质量取决于"谁在场"，不取决于"证据是什么" |
| **2** | 趋势信息搜集 | 研究员 70% 时间在搬运信息（翻 TikTok、截图、贴 Excel），只有 30% 在分析，价值完全倒挂 |
| **3** | 上市后复盘 | 复盘靠人记、靠人写，经验存在离职员工的脑子里。这次踩过的坑，换个品类照踩 |
| **4** | 跨角色对齐 | 趋势报告是 PPT，销量数据是 Excel，IP 信息在邮件里——三种语言互不相通，洞察在传递中衰减 |

### 1.4 为什么做这个项目

瓶颈不在"执行效率"（名创的执行已经是世界级），而在**决策质量和决策速度**。AI 自动写文案、自动翻译解决不了这个问题，能解的是把评审会本身重构掉——这就是 AI Product Committee 的出发点。

## 二、用户与交互逻辑

### 2.1 用户是谁

**用户不是消费者，是名创内部商品开发角色**：第一用户是商品经理/商品企划，第二用户是市场研究员、IP 经理、海外运营。

### 2.2 输入设计：为什么是"品类 + 目标市场 + 预算区间"

三个输入不是拍脑袋选的，依据是它们分别锁死零售开发的三个硬约束：

| 输入 | 锁死的约束 | 没有它会怎样 |
|:---|:---|:---|
| 品类 | 决定调哪个知识库、参考哪些历史案例、适用什么供应链 | 系统不知道"潮玩"和"美妆"的趋势信号完全不同源 |
| 目标市场 | 决定数据源权重——泰国看 TikTok/Shopee，日本看礼品属性，国内看小红书/B站 | 全球数据一锅烩，结论必然平庸 |
| 预算区间 | 决定可行解空间——头部 IP 授权费百万级，新锐 IP 几万级，预算直接砍掉一半候选 | 创意官会生成一堆根本签不起的方案 |

**考虑过但刻意没放进默认输入的维度**：时间窗口（上市 deadline 影响该押上升期还是峰值期趋势）、战略意图（走量款/利润款/形象款）、渠道（线上/线下/旗舰店）、自有产品线避让。这些做成了**高级选项、带默认值**——渐进式披露原则：首次使用填三个框就能跑，跑熟了再展开。默认三要素是"缺了就无法界定问题"的最小集，其余是"缺了可用合理默认"的优化项。

### 2.3 一次完整使用的交互流程

1. **输入**：商品经理用自然语言发起（"帮我看看东南亚市场下季度潮玩品类的机会"），或填结构化 brief（品类+目标市场+预算区间）
2. **AI 委员会自动开会**：七位 Agent 按圆桌流程各抒己见，**全程可旁观、可打断**（打断机制详见 5.5）
3. **产出**：《商品立项建议书》——每个候选方案带五维评分、证据链、风险提示
4. **人的动作**：点开任何一条结论可看到背后的数据来源（EvidenceRef）；不认可某个权重，调完重跑（权重机制详见 5.4）；最终拍板"立项/暂缓/否决"
5. **闭环**：上市后真实销量回流，学习官更新模型，下次更准

### 2.4 人与 AI 的边界

- **AI 负责"把会开好"，人负责"拍板"**。AI 从不说"这个一定爆"，只说"基于这些证据，机会值 83 分，主要风险是竞品密度"
- **事实核查权在人**：每条结论挂证据链接，一键可验证，AI 无法黑盒忽悠
- **参数主权在人**：五维权重是暴露给商品经理的可调参数，不是埋在代码里的黑盒

划界标准只有一条：**凡是需要为结果负责的决定，留给人；凡是信息搜集、结构化、交叉验证的工作，交给 AI。**

## 三、四层架构详解

### 3.1 架构总览

```
反馈学习层 ←——— 上市数据回流，反哺下面三层
    ↑
决策引擎层 ←——— 汇聚评审意见，输出建议书，人确认
    ↑
Agent 协同层 ←—— 七位委员圆桌会议
    ↑
数据底座层 ←——— 五元真实数据源
```

### 3.2 数据底座：五元数据、重要度排序、隐私权限

**"多元数据"具体是哪五元、怎么获得**（实测过，非纸上谈兵）：

| 排序 | 数据元 | 具体来源 | 获取方式 | 排序依据 |
|:---:|:---|:---|:---|:---|
| 1 | 消费需求信号 | 淘宝搜索联想词 | 公开接口直连 | 离购买行为最近，是 intent 不是 attention |
| 2 | 企业内部知识 | 飞书知识库（爆品案例、IP授权信息、历史商品数据） | 飞书开放 API | 独有性最强、区分度最高（依赖企业授权） |
| 3 | UGC 趋势信号 | B站分区排行榜 | 公开 API | Z 世代先行指标，比搜索数据早 2-4 周 |
| 4 | 海外搜索趋势 | Google Trends | pytrends | 覆盖广但粒度粗、略滞后，做校验用 |
| 5 | 社媒舆情 | 小红书/TikTok | 预采集真实快照 | 噪声最大、获取最难，做补充佐证 |

**实测结论**：淘宝联想词和 B站排行已在当前网络环境跑通真实数据（Labubu/Chiikawa 真实需求词、5 分区 474 个真实排行视频）；Google Trends 代码就绪、需海外网络；小红书/TikTok 直连反爬严重，比赛用真实快照并公开采集方法论。**诚实的工程策略：能直连的实时跑，不能直连的用快照，每个源的获取方式都写清楚——这比假装全能爬有说服力得多。**

**隐私与权限分三层处理**：
- **公开数据层**：遵守 robots.txt 和频率限制，优先官方 API；小红书/TikTok 生产版走官方开放平台（灵犀/蒲公英等），宁可少一个源，不踩合规线
- **企业数据层**：跑在飞书权限体系内，Agent 只读被授权的知识库空间，数据不出企业域
- **用户数据层**：评论只做群体级聚合分析（情绪分布、痛点聚类），不做个体画像、不存可识别个人的信息

顺手红利：**EvidenceRef 证据链天然就是审计轨迹**——每条结论能反查数据源和时间，合规审查时就是现成台账。

### 3.3 Agent 协同层

七位拟人化委员，详见第四章。

### 3.4 决策引擎层

汇聚商业官与全球化官的双轨评审意见，按五维权重合成机会值，输出《商品立项建议书》，然后 **interrupt 挂起，等商品经理确认**——决策权不下放给机器。

### 3.5 反馈学习层

学习官采集上市后数据，完成"预测-结果"配对、偏差归因、权重校准建议，反哺全委员会。详见第六章。

## 四、AI 商品委员会：Agent 设计

### 4.1 七位委员与岗位映射

| AI 委员 | 对应名创岗位 | 核心输出 | 解决的问题 |
|:---|:---|:---|:---|
| 🔍 趋势官 | 市场研究总监 | 全球趋势报告、趋势热度指数 | 趋势难捕捉 |
| 👥 用户官 | 用户研究负责人 | 用户画像、痛点清单、购买动机 | 不了解消费者 |
| 🧸 IP官 | IP 合作经理 | IP 热度榜、联名推荐、生命周期预测 | IP 选择困难 |
| 🎨 创意官 | 商品策划经理 | 3-5 个商品方案（带证据溯源） | 创意效率低 |
| 💰 商业官 | 财务&商品委员会 | 五维机会值评分、推荐等级 | 选品难决策 |
| 🌍 全球化官 | 海外运营负责人 | 上市国家、定价、本地化策略 | 全球策略难定 |
| 📈 学习官 | 数据分析负责人 | 复盘报告、模型优化、经验沉淀 | 反馈不闭环 |

**数量为什么控制在 7 个**：每个 Agent 一一对应名创真实岗位，多一个是为多而多，少一个就有维度没人负责。**Agent 数量由组织架构决定，不由技术炫技决定。**

**Agent 要不要和真实经理对接**：要，但分阶段，且一开始就设计好人机权责——
- Phase 1（比赛/MVP）：不逐一绑定，AI 委员会作为虚拟团队整体服务商品经理，先证明价值
- Phase 2（企业落地）：每个 Agent 成为对应岗位经理的"数字幕僚"，三个机制：
  1. **认领制**：每个 Agent 有一个真实人类 owner 对其输出质量负责（趋势官归市场研究总监"管"）
  2. **反馈通道**：owner 对 Agent 输出的纠正（采纳/驳回/标注误判）回流学习官——这是比销量数据更高频的学习信号
  3. **责任不动**：业务责任永远在人类经理身上，Agent 没有决策权

最后这条是**组织接受度的生命线**：让经理觉得 AI 是自己的兵，不是来抢椅子的。凡是让一线经理感到被替代的 AI 项目，死于内部抵制的概率远大于死于技术不行。

### 4.2 协作拓扑：为什么这样连线

```
趋势官 ┐
用户官 ┼─→ 创意官 ─┬─→ 商业官 ──┐
IP官  ┘           └─→ 全球化官 ─┴─→ Decision Engine ─→ 学习官 ─┐
        （并行汇聚）    （双轨并行）                              │
        ↑←——————————————— 反馈优化 ———————————————————————┘
```

洞察类三官彼此独立、可并行；创意依赖三方全部输入，必须等；商业评估和全球化策略是两个独立维度，不该串行等待——所以双轨并行。连线原则：**有数据依赖才连线，没依赖就并行。**

### 4.3 为什么用 LangGraph 而不是别的

| 维度 | LangGraph | CrewAI | AutoGen |
|:---|:---|:---|:---|
| 控制流 | **显式状态图，精确控制每个跳转** | 角色扮演式，流程靠 prompt 约定 | 对话驱动，自由度高但难约束 |
| 并行+汇聚 | 原生支持 fan-out/fan-in | 支持但粒度粗 | 需手动实现 |
| 循环回路 | **原生支持**（反馈学习层的核心） | 不擅长 | 不擅长 |
| Human-in-the-loop | **原生 interrupt/resume** | 弱 | 需自行封装 |
| 状态持久化 | checkpoint，会议可暂停续跑 | 无 | 弱 |
| 团队储备 | **DAGents-InsightFlow 已验证 10 节点 DAG** | 无 | 无 |

三个决定性理由：
1. **我们的流程不是流水线，是图**——创意官汇聚三方输入（fan-in）、商业官和全球化官并行（fan-out）、学习官形成回路（cycle），LangGraph 的图模型与之同构
2. **评审必须能暂停等人**——Decision Engine 产出建议书后 interrupt，等商品经理确认再 resume，这是 LangGraph 招牌能力
3. **团队已在 DAGents 项目踩过坑**（声明式 Runtime、NodeSpec 解耦、Human-in-the-Loop 均验证过），直接复用，不重复交学费

### 4.4 MVP 边界：为什么是 5 个 Agent 而不是 3 个

3 个 Agent（趋势→创意→商业）的问题：**那是一条流水线，不是圆桌**，验证不了最大差异化假设——"多角色协同决策优于单角色直出"。3 个 Agent 的 MVP 等于抽掉灵魂只剩骨架，评委会看到一个普通的串联工作流。

修正后的 MVP 口径：
- **工程验证层（内部里程碑）**：先联通 3 个，确认"数据进→方案出→评分出"链路通
- **价值验证层（对评委的 MVP）**：必须 5 个起——趋势/用户/IP/创意/商业。圆桌的最小可信结构是"**至少两个独立信息源汇聚到一个节点**"，5 个 Agent 才第一次出现"汇聚"拓扑；要演示的核心场景就是"三方洞察在创意官那里交汇碰撞"，少于 5 个演不出来
- 全球化官和学习官放 Phase 2：前者是横向扩展，后者比赛期内本来只能演示机械结构

**MVP 的大小不由"最少几个能跑"决定，由"最少几个能验证核心假设"决定。**

## 五、圆桌会议机制

### 5.1 五幕审议流程

| 幕 | 发生什么 | 类比真实会议 |
|:---:|:---|:---|
| 一 | 趋势官/用户官/IP官各自陈述洞察，**每条带证据** | 会前汇报环节 |
| 二 | 创意官基于三方输入提 3-5 个方案 | 头脑风暴 |
| 三 | 商业官打分、全球化官定策略，**同时进行** | 各部门分头评审 |
| 四 | Decision Engine 汇总，输出建议书 | 主持人收拢结论 |
| 五 | （上市后）学习官复盘，反哺全员 | 季度复盘会 |

### 5.2 候选方案是怎么产生的

不是创意官一个人"灵光一现"，是一条**受约束的组合生成链**：

```
趋势官产出：什么在热（信号：Labubu 搜索增速、桌面美学话题）
用户官产出：缺什么（信号：收藏痛点"盲盒没地方放"、价格敏感带 ¥39-79）
IP官产出：搭谁的车（信号：治愈系 IP 东南亚付费意愿高 40%）
        ↓ 三方材料 + 两个约束
创意官做组合：趋势 × 需求 × IP × 商品形态
             （形态信号来自淘宝联想词：娃衣/挂件/盲盒/摆件/香薰……）
        ↓ 预算区间过滤（签不起的 IP 组合直接砍掉）
        ↓ 历史爆品特征库锚定（RAG 召回相似成功案例）
产出：3-5 个差异化方向，每个标注"依据了哪几条证据"
```

方案产生涉及**四个 Agent + 知识库 + 输入约束**。创意官是合成器，不是凭空生成器——评委追问"方案哪来的"，答案是"每条都能倒推回数据"，而不是"大模型想的"。

### 5.3 机会值评分：83 分的解剖

**谁定**：商业官 Agent 计算输出，但计算规则是人定的，且每个分项可拆解。83 的完整解剖：

```
83 = 趋势热度 92×35% （趋势官给分，证据：搜索增速180%、跨平台广度）
   + 用户需求 78×25% （用户官给分，证据：痛点密度、需求广度）
   + IP适配  85×20% （IP官给分，证据：IP热度×品类匹配×区域偏好）
   + 竞争程度 60×10% （竞品越多分越低，证据：同类在售数量）
   + 历史相似 70×10% （知识库相似案例的历史表现）
```

每个分项由**拥有该数据的 Agent 独立给出**，必须挂 EvidenceRef——83 是一笔**可追溯的算术，不是一种感觉**。

必须说的实话：**机会值的绝对值不如相对排序和分解结构重要**。评审的真实场景是"83 vs 76 vs 71，选谁、为什么"——决策价值在对比和归因里，不在 83 本身有多精确。"83 和 84 有什么本质区别"的答案是"没有，别纠结个位数，看分项结构"。

### 5.4 权重机制：确认、依据、修改后从哪重跑

**初始确认**：评审正式开始前有"权重确认"环节，首次使用强制，后续沿用上次配置。

**确认方式**：滑杆面板 + **预设模板**。模板比裸滑杆重要——大多数经理不想研究权重，他们想选"这次是走量款评审"（用户需求权重自动调高）还是"形象款评审"（趋势热度权重调高）。模板把参数问题翻译成业务语言。

**默认权重依据**（按优先级）：
1. **历史回测**：用已完结的爆品/扑街案例，调权重使系统评分对两类的区分度最大——主依据
2. 行业先验：趋势衰减最快、时间价值最高，趋势热度占 35% 居首
3. 学习官事后校准（长期修正项）

**修改后从哪重跑**：只重跑**商业官评分 + Decision Engine 聚合**，洞察层完全不动。这是刻意设计的架构属性——**数据层与权重层解耦**：趋势数据、用户评论不因权重变了而变化，变的只是合成方式。调权重重跑成本是秒级，不是重开一次会。若哪天调权重要重跑数据层，说明架构耦合了，那是 bug。

### 5.5 打断机制：谁旁观、谁打断、打断后的路径

- **谁旁观**：发起评审的商品经理是第一旁观者；委员会其他角色可围观各自相关环节。旁观界面即圆桌直播——哪位委员正在发言、引用了什么证据，实时可见
- **谁打断**：只有人有打断权，Agent 之间不打断
- **怎么实现**：LangGraph interrupt + checkpoint 持久化。每个 Agent 节点执行前后是天然断点，状态整体落盘；打断 = 断点挂起，恢复 = 载入 checkpoint 续跑。技术上没有"杀进程重来"，只有"挂起-注入-续跑"

**打断后的路径设计——分三类，对应三种重跑范围**：

| 打断类型 | 例子 | 重跑路径 |
|:---|:---|:---|
| 质疑型 | "趋势官说 Labubu 在上升期，证据我看不懂，解释一下" | 只重跑趋势官（附带质疑上下文），下游不动 |
| 补充型 | "这个 IP 上个月已被竞对独家签走" | 注入共享状态 → 失效传播分析：IP官、创意官、商业官受影响 → **从最早受影响的节点起重跑** |
| 方向型 | "摆件不看了，改看收纳方向" | 修改约束 → 从创意官起重跑，洞察层数据复用 |

核心原则是**最小失效重跑**——依赖图本来就在 LangGraph 里，打断后顺依赖边向下游标脏，只重跑标脏的子图。整场会推倒重来是设计失败。

### 5.6 产物与导出：《商品立项建议书》

结构化包含：候选方案清单、五维机会值评分、每个维度的证据链、风险提示、上市节奏建议、待定事项。

**导出方式**：Markdown/PDF 报告 + 写入飞书多维表格（立项台账）+ 推送飞书文档。

### 5.7 为什么是 3-5 个方案：与"711 漏斗"的关系

**系统不替代"1 万→100"的漏斗，重构的是漏斗上游的"方向选择"**：

```
我们的产出：3-5 个方向（如"桌面摆件系列"）
    ↓ 每个方向由设计团队展开成几十上百个 SKU 设计稿
名创原有漏斗：~1 万个设计稿 → 100 个打版
```

我们不管"画 1 万张图"，也不管"选 100 款打版"，管的是**"这 1 万张图该往哪些方向画"**。传统模式下 1 万个 idea 里大量是方向性试错——方向错了，画得再精美也是废稿。我们的价值是**提高进入漏斗的 1 万个 idea 的方向命中率**。

**为什么是 3-5 个**：
1. **认知负荷上限**：一场评审会里人能有效讨论的互斥方案就是 3-5 个，给 20 个等于没筛选
2. **差异化约束**：3-5 个必须在形态/场景/价位上互相差异（摆件 vs 收纳 vs 香薰夜灯），而不是同一方向的微调变体——委员会需要的是**真正的选择空间**，不是虚假的丰富感

### 5.8 想法来源、好处与风险

**为什么做圆桌会议、想法从哪来**：来自对痛点第一名的分析——评审会的病根是"没有任何一个角色掌握完整信息"。圆桌会议的本质不是让 AI 聊天，而是**用制度设计保证每个决策维度都有人负责、每条结论都有证据、每次交锋都被记录**。借鉴的是真实企业治理中的委员会制，不是多智能体论文的噱头。

**好处**：可解释（每票有据）、不遗漏（维度全覆盖）、组织即插即用（映射现有委员会，不改变名创组织形态）。

**风险（诚实面对）**：
1. **"表演化"风险**——七个 Agent 若是同一模型换七个 system prompt 自说自话，圆桌就是剧本不是审议。**解法：让每个 Agent 独占不同数据源**（趋势官只看得见趋势数据，用户官只看得见需求数据），信息差是真实的，汇聚才有增量。这是真圆桌和假圆桌的分水岭
2. **错误传播**——趋势官看走眼，创意官跟着错。解法：证据链强制绑定 + ReviewAgent 质检（无证据的结论打回）
3. **成本与延迟**——7 个 Agent × 多轮 LLM 调用。解法：非关键路径用小模型，洞察层缓存复用
4. **效果证明难**——怎么证明圆桌比单 Agent 决策好？解法：测试集消融实验（单 Agent vs 委员会对同一批历史案例的决策质量对比），详见第七章

## 六、反馈学习与数据飞轮

### 6.1 先纠正措辞：不是"预测热点"，是"早期识别热点"

这是评委最容易攻击的点，方案里必须始终用后者。为什么热点**可早期识别**，三个依据：

1. **热点有"前震"**——搜索量增速、社媒讨论量增速、跨平台迁移，这些信号在峰值前数周就出现。我们赚的不是"预言"的钱，是"**比人工早发现 2-4 周**"的钱；名创打版周期正好 2-4 周，早发现 2 周 = 赶上窗口期，这就是商业价值的时间换算
2. **传播有结构**——热点扩散路径相对固定：核心圈层（小红书/B站核心用户）→ 大众平台（抖音/淘宝搜索）。**不同平台信号的时间差本身就是预测因子**——B站冷、淘宝热（实测中 Labubu 正是这个形态）说明它处于扩散后期而非上升早期，这个判断直接改变 IP官的联名建议
3. **历史同构**——治愈系 IP 的生命周期曲线形状相似（Molly→Labubu→Chiikawa），可用历史曲线做模式匹配，估计当前处于曲线哪一段

**同样重要的是说什么不可预测**：黑天鹅式爆红不可预测、精确峰值时点不可预测。系统从不输出"它一定爆"，输出的是"它处于上升期、当前增速 X、历史同类型窗口期 6-9 个月"——**概率性研判，不是确定性预言**。一句话：热点不可预言，但可早期识别；你无法预言哪朵云会下雨，但可以盯着气压计提前收衣服。

### 6.2 上市后真实销量怎么获得、演示用什么数据

**生产环境**：名创 POS/ERP 按 SKU 回流，经飞书多维表格关联到当初的立项记录。

**比赛演示环境**，两条路并行：
- **电商公开数据做代理**：天猫/淘宝月销量、Amazon BSR 排名变化、Shopee 销量——公开可见的真实销量代理指标
- **"时光机回测"（主打方案）**：取已完结的公开案例（如某已验证的 IP 联名），**只用其上市前时间点的数据**喂给系统做"预测"，再与公开的后续结果对照。这把"比赛周期内无法验证"变成"可验证的回测"，评委能当场核对

演示时明确声明数据口径——哪部分实时抓的、哪部分历史回放的。这种诚实反而是加分项。

### 6.3 怎么知道踩中了、学习官返回什么、怎么保证迭代有利

**怎么知道踩中了**：上市前系统评分 vs 上市后实际结果对照，四个指标：首月销量达成率、动销率、售罄率、社媒声量延续性。

**学习官返回什么**：
- 预测偏差报告：83 分的方案实际表现如何，五个维度哪个最准、哪个最偏
- 归因分析：爆的为什么爆（哪个信号是真的），哑的为什么哑（哪个信号误导了）
- 新维度发现：如"日本市场包装礼品化程度"这种评估清单里原来没有的因子
- 权重校准建议：连续 N 期某维度偏差最小 → 建议上调其权重

**怎么保证迭代有利——四条纪律**：

| 纪律 | 防什么 |
|:---|:---|
| **样本量纪律**：单次结果不调权重，积累 N 期才调 | 防单次噪声过拟合——一个爆款可能是运气 |
| **版本控制**：每次变更存版本、可回滚 | 迭代变差了能退回上一版 |
| **影子模式**：新权重先与旧权重并行评分几期，对比后才切换 | 防"改了更差"直接上线 |
| **人类批准制**：学习官只提建议，**无自动改参权** | 防系统在低质量数据上自我强化、越学越歪 |

迭代路径：数据回流 → 偏差归因 → 假设生成 → 影子验证 → 人批准 → 灰度生效 → 持续监控。

### 6.4 数据飞轮具体怎么做到

飞轮不是口号，是三个机械部件：

**部件一：决策留痕**。每次评审的建议书、分项评分、证据链、以及**最终人工决定**（包括人否决 AI 建议的情况）全部写入多维表格台账。没有留痕就没有飞轮——大多数团队飞轮失败就死在第一步：只存了结果，没存"当初为什么这么决策"。

**部件二：结果配对回流**。上市后数据按 SKU 关联回当初的立项记录，形成"**预测-结果**"配对结构。单独的预测和单独的结果都没有学习价值，配对了才有。

**部件三：周期性校准动作**。学习官按月出偏差报告 → 权重校准建议 → 人批准 → 版本化生效。同时验证过的成功案例特征沉淀进知识库，创意官下次生成时 RAG 召回——"上次什么成了"直接影响"下次生成什么"。

**飞轮转速怎么度量**：每月计算预测偏差率（评分与实际结果的误差/相关系数），偏差率逐月收窄 = 飞轮在转的客观证据，这个指标本身就可放进给名创的汇报。

**冷启动**：飞轮不从零转——先用 30-50 个历史回测 case 灌入"预训练经验"，系统上线第一天就带着几十次"虚拟评审"的经验。

**比赛期间的诚实口径**：真实飞轮需要上市周期，比赛内转不起来。比赛展示的是**飞轮的机械结构**——用回测数据完整模拟一圈"预测→对照→归因→校准→复评"，证明每个部件都能转，而不是声称飞轮已经在转。

## 七、测试集与效果验证

### 7.1 三层测试集设计

| 测试集 | 规模 | 用途 | 数据来源 |
|:---|:---:|:---|:---|
| **历史回测集** | 30-50 case | 验证委员会决策质量、跑消融实验 | 公开爆品编年史：新闻报道、财报、行业盘点还原案例——爆/平/扑各约 1/3 分层抽样（Labubu 2024、Chiikawa 联名、哈利波特联名，**以及同等数量的失败联名案例**） |
| **单元测试集** | 每 Agent 20-30 case | 回归测试，改 prompt/权重不劣化 | 正常 case + 边界 case + 异常 case（数据缺失、来源不足） |
| **对抗测试集** | 10-20 case | 压力测试 | 故意构造：信号冲突（淘宝热但 B站冷）、伪趋势（短期脉冲后熄火）、证据不足 |

### 7.2 两条生命线纪律

1. **时点截取**：每个回测 case 只用"决策时点之前"公开可得的数据做输入，严禁未来信息泄露（lookahead bias）——否则回测一文不值
2. **必须有失败案例**：只测爆品的测试集只会验证幸存者偏差，扑街案例占比不低于 1/3

### 7.3 消融实验：证明圆桌的价值

用同一批历史回测 case 跑对照：单 Agent 直出 vs 五 Agent 圆桌，比较决策质量（与实际结果的吻合度）。这是"AI 应用深度"评分维度的直接证据，也是回应"多 Agent 是不是噱头"的硬答案。

## 八、飞书 AI 能力集成

### 8.1 三方关系

**名创优品出场景和命题，飞书出 AI 基建，我们的方案是"场景 × 基建"的粘合层**。命题原文要求"借助飞书 AI 工具"，飞书能力不是锦上添花，是指定动作。

### 8.2 逐项用法

| 飞书能力 | 在项目里的角色 | 具体用法 |
|:---|:---|:---|
| **企业豆包** | 七位委员的统一推理引擎 | 每个 Agent 通过 API 调豆包，system prompt 注入角色+职责+输出格式。统一引擎：推理质量一致、成本可管、数据不出企业权限体系 |
| **飞书 Aily** | 把代码版委员会"产品化" | 后端代码跑重逻辑，Aily 用低代码把工作流暴露给业务方——商品经理不懂代码，也能在可视化界面发起评审、调权重、看结果。**这是 AI 从 Demo 变成业务工具的关键一跳** |
| **妙搭** | 快速搭建立项 Dashboard | 机会值看板、趋势热力图、方案对比页的展示层，不用手写前端全套 |
| **多维表格** | 系统的"台账数据库" | 每个候选商品一行：评分、状态（待评审/已立项/已打样/已上市）、证据链接全在里面流转；**智能体进群**，商品经理直接在群里问"当前 80 分以上的方案有哪些"。同时它也是飞轮部件一"决策留痕"的载体 |
| **妙记** | 两个巧思用法 | ① 把 AI 委员会的完整辩论过程转录成"会议纪要"格式存档——AI 开的会也留痕；② 真实人类评审会用妙记记录，回流知识库，作为校准 AI 决策的参照数据 |

### 8.3 与名创优品的连接点

每个 Agent 对应名创真实岗位、每张表对应名创真实流程（商品委员会、立项、打样、上市），五维评分维度设计来自名创"兴趣消费+IP 战略"的业务逻辑。即使名创内部协作平台不是飞书，架构也可移植——Agent 层对 LLM 不敏感，豆包可换。

## 九、商业化路径

### 9.1 第一层：名创优品内部落地（0-1）

- **切入点**：单品类试点——潮玩（TOPTOY 体系），5 个核心 Agent，只接公开数据，零内部数据依赖即可起步
- **验证指标**：评审会准备时长（目标降 80%）、单方案信息完整度、研究员信息搜集工时
- **扩张路径**：品类扩展 → 接入内部 SKU/销售/库存数据（评分维度升级）→ 商品开发中台

### 9.2 第二层：行业 SaaS 化（1-N）

四层架构本身行业无关——换成美妆就是"成分趋势官+肤质洞察官"，换成食品就是"口味趋势官"。目标客户是**有高频上新压力的行业**：快消、IP 消费品、新消费品牌。收费模式：按品类订阅 + 定制实施费。轻量版（纯公开数据）低门槛获客，企业版（接内部数据+私有部署）做客单价。

### 9.3 第三层：真正的壁垒

壁垒不在代码——代码三个月就能被抄走。壁垒在**反馈学习层滚起来的数据飞轮**：每服务一个客户、每经历一次上市复盘，权重库、评分校准、品类知识就厚一层。先发者的第 100 次评审质量，是后来者第 1 次追不上的。这就是为什么从第一天就把学习官设计进架构——它决定这是个"工具"还是个"越用越聪明的资产"。

### 9.4 诚实的边界条件

商业化成立的前提是客户愿意回流上市数据；纯公开数据版本的价值天花板是"信息效率工具"，接入内部数据才升级为"决策引擎"。所以商业模式上必须设计让客户有动力开放数据的机制——例如：接入内部数据后评分维度和准确率**可见地提升**，用效果换授权。

## 十、风险登记册

| 风险 | 本质 | 应对 |
|:---|:---|:---|
| 圆桌"表演化" | 同一模型换 prompt 自说自话，审议是假的 | 每个 Agent 独占不同数据源，信息差真实存在，汇聚才有增量 |
| 错误传播 | 上游 Agent 看走眼，下游跟着错 | EvidenceRef 强制绑定 + ReviewAgent 质检，无证据结论打回 |
| 成本与延迟 | 7 Agent × 多轮 LLM 调用 | 非关键路径用小模型；洞察层缓存复用；MVP 先 5 个 |
| 效果证明难 | 无法证明圆桌优于单 Agent | 历史回测集 + 消融实验，用数据回答 |
| 学习官越学越歪 | 低质量数据上自我强化 | 迭代四纪律：样本量纪律、版本控制、影子模式、人类批准制 |
| 数据合规 | 平台 ToS、用户隐私 | 公开源守 robots 与频率限制；生产版走官方开放平台；评论只做群体聚合 |
| 组织抵制 | 一线经理感到被替代 | 责任不动原则：Agent 无决策权，定位是"数字幕僚"不是"数字替身" |
